# HitCam Vision: распознавание объектов

HitCam для ПК умеет находить объекты в видео с телефона — людей, кружки, собак и ещё 77 классов из набора COCO
«из коробки» — и рисовать вокруг них рамки. Модель можно дообучить на **своих** предметах; всё для этого лежит в
папке [`vision/`](../vision/README.md). Этот документ объясняет, как всё устроено, почему выбрана именно такая модель
и что нужно знать новичку, чтобы обучение получилось.

## Как это работает

```
телефон ──H.264 по Wi-Fi──▶ ПК: декодер ──▶ кадр ──┬──────────────────────────────▶ окно превью / виртуальная камера
                                                    │                                    ▲
                                                    └─▶ уменьшенная копия 384×384 ──▶ RF-DETR (ONNX, DirectML)
                                                          ──▶ рамки + классы + уверенность ──▶ трекер ──▶ рисование
```

1. **Телефон** снимает и сжимает видео в H.264 и отправляет его на ПК по Wi-Fi (см. [protocol.md](protocol.md)).
2. **ПК** декодирует поток (Media Foundation) в обычные кадры — те же, что видны в окне превью и уходят в
   виртуальную камеру.
3. **Подготовка кадра для модели.** Копия кадра растягивается до квадрата входа модели (384×384 для Nano, 512×512 для
   Small) без полей по краям (`"resize": "stretch"`), переводится в RGB, яркости делятся на 255 и нормализуются
   средним и разбросом ImageNet (`mean`, `std` из labels.json). Масштабирование — обычное билинейное без
   сглаживания (как `cv2.INTER_LINEAR` и как в PyTorch-коде RF-DETR); сглаживающее уменьшение (PIL, «area»)
   сдвигает уверенность на мелких объектах на 0,05–0,1.
4. **Модель** — RF-DETR в формате ONNX — выполняется через ONNX Runtime с DirectML: это DirectX 12, поэтому
   работает на любой видеокарте (NVIDIA, AMD, Intel), без CUDA. На RTX 3070 RF-DETR Nano тратит около 9 мс на
   кадр, Small — около 16 мс; на процессоре — 120–150 мс.
5. **Расшифровка выхода.** Модель выдаёт 300 «кандидатов» (запросов, queries): для каждого рамку `dets`
   (центр x, центр y, ширина, высота в долях кадра) и по числу на класс в `labels` (логиты). Уверенность =
   сигмоида логита; остаются пары «кандидат–класс» с уверенностью выше порога (обычно 0,5). NMS не нужен (см. ниже).
6. **Трекер** связывает рамки соседних кадров в «один и тот же объект»: по перекрытию рамок (IoU) и классу. Это
   убирает мигание (объект пропал на один кадр — рамка не исчезает), сглаживает дрожание рамок и позволяет
   различать объекты одного класса между кадрами.
7. **Рисование.** Рамки с подписями выводятся поверх превью и, если включено, «впекаются» в видео, которое
   получают Zoom, OBS и другие программы через виртуальную камеру.

### Файлы модели

HitCam ищет модели в `%LOCALAPPDATA%\HitCam\models\`: пара `<имя>.onnx` + `<имя>.labels.json`.

```json
{
  "name": "RF-DETR Nano (COCO)",       // как модель называется в списке HitCam
  "format": "rfdetr",                   // формат выходов (dets + labels, см. выше)
  "input": [384, 384],                  // ширина и высота входа
  "mean": [0.485, 0.456, 0.406],        // нормализация RGB: (x / 255 - mean) / std
  "std": [0.229, 0.224, 0.225],
  "resize": "stretch",                  // кадр растягивается до входа без полей
  "outputs": {"boxes": "dets", "logits": "labels"},   // имена выходов ONNX
  "classes": {"1": "person", "2": "bicycle", "...": "..."},   // номер столбца labels → имя класса
  "license": "Apache-2.0"
}
```

(Комментарии здесь только для пояснения — в настоящем JSON их нет.) Номер в `classes` — это номер столбца в выходе
`labels`. У стандартной COCO-модели столбцов 91 и номер равен id категории COCO (1 = person, 90 = toothbrush;
11 номеров COCO не использует, у них нет имени). У дообученной модели классы нумеруются 0, 1, 2, … в порядке id
категорий из разметки, плюс последний служебный столбец «не объект» без имени. Столбцы без имени HitCam
пропускает. Модель экспортируется в FP32: FP16-версия на DirectML у нас не заработала.

## Почему RF-DETR

**RF-DETR** (Roboflow, 2025) — детектор реального времени семейства DETR с основой DINOv2. Для нас важно:

- **Лицензия Apache 2.0** и у кода, и у весов Nano / Small / Medium / Base / Large. Модели и дообученные на их
  основе веса можно свободно встраивать и распространять вместе с HitCam (лицензия MIT). Самые большие варианты
  (XLarge, 2XLarge) идут под другой лицензией Roboflow — мы их не используем.
- **Точность и скорость.** По опубликованным результатам Nano точнее самых маленьких YOLO при сравнимой скорости,
  а сильная предобученная основа (DINOv2) помогает, когда своих картинок мало.
- **Без NMS**: выход модели — сразу ответ, это проще и одинаково на всех платформах.
- **Экспорт в ONNX** штатный, модель работает через DirectML без переделок.

**Почему не Ultralytics YOLO** (YOLOv5, v8, 11): и библиотека, и веса распространяются под **AGPL-3.0**. AGPL
требует открыть под AGPL весь продукт, который включает такую модель или отдаёт её результаты пользователям (в том
числе по сети), либо купить коммерческую лицензию Ultralytics. Для проекта под MIT это не подходит: мы не можем
ни положить такую модель в сборку, ни рекомендовать её пользователям для HitCam, не навязав им эти условия.
Другие открытые альтернативы с разрешительными лицензиями — RT-DETR, D-FINE, YOLOX (все Apache 2.0) — тоже
годятся; RF-DETR выбран за простое дообучение и хороший баланс скорости и точности на маленьких вариантах.

## Немного теории

### Что выдаёт детектор

Классификатор отвечает на вопрос «что на картинке». **Детектор** отвечает «что и где»: список объектов, у каждого
- **рамка** (bounding box) — прямоугольник, параллельный краям кадра: `x1, y1, x2, y2` (углы) или `cx, cy, w, h`
  (центр и размеры), в пикселях или в долях кадра;
- **класс** — одно из имён, которым модель обучали;
- **уверенность** (confidence, score) от 0 до 1 — насколько модель уверена, что тут объект этого класса.

**Порог уверенности** — главная ручка у пользователя. Порог выше — меньше ложных рамок, но больше пропусков; ниже —
наоборот. Для показа на экране обычно берут 0,4–0,6.

### IoU — насколько совпадают две рамки

**IoU** (Intersection over Union) = площадь пересечения / площадь объединения двух рамок. 1 — рамки совпадают,
0 — не пересекаются. 0,5 — заметно сдвинутые, но «про один объект»; 0,9 — почти одинаковые. IoU используется везде:
засчитать ли ответ модели как правильный (обычно при IoU ≥ 0,5 с настоящей рамкой), склеить ли рамки в трекере,
проверить, что ONNX-версия отвечает так же, как исходная (`export.py` требует IoU ≥ 0,95).

### NMS и почему DETR он не нужен

Классические детекторы (YOLO, SSD, Faster R-CNN) предлагают для каждого объекта десятки похожих рамок из соседних
ячеек сетки. Чтобы оставить одну, применяют **NMS** (non-maximum suppression): берут рамку с наибольшей
уверенностью, выбрасывают все рамки того же класса, которые перекрываются с ней сильнее порога (IoU 0,5–0,7),
повторяют. У NMS свои проблемы: порог надо подбирать, в толпе он «съедает» соседние объекты, это лишний шаг,
который по-разному реализован на разных платформах.

**DETR** (DEtection TRansformer) устроен иначе: у модели фиксированный набор «запросов» (у RF-DETR их 300), и при
обучении каждому настоящему объекту венгерским алгоритмом назначается ровно **один** запрос. Остальные учатся
отвечать «ничего нет». Дубли наказываются самим обучением, поэтому на выходе сразу готовый список — без NMS.
На практике у недоученной модели изредка бывает слабый дубль (например 0,62 и 0,46 на одном объекте после
нескольких эпох) — его отсекают порог уверенности и трекер.

### Как мерить качество

Сравниваем ответы модели с разметкой на картинках, которые она не видела:
- **TP** (true positive) — рамка модели совпала с настоящим объектом того же класса (IoU ≥ 0,5);
- **FP** (false positive) — рамка есть, объекта нет (или не тот класс, или рамка «мимо»);
- **FN** (false negative) — объект есть, модель его не нашла.

**Точность** (precision) = TP / (TP + FP): какая доля найденного — правда. **Полнота** (recall) = TP / (TP + FN):
какая доля настоящих объектов найдена. Они зависят от порога уверенности и тянут в разные стороны.

Если перебрать все пороги, получится кривая «точность–полнота»; площадь под ней — **AP** (average precision) одного
класса, от 0 до 1. **mAP** — среднее AP по классам. Два варианта:
- **mAP@50** — рамка засчитывается при IoU ≥ 0,5. Отвечает на вопрос «находит ли модель объекты».
- **mAP@50:95** — среднее по порогам IoU 0,50, 0,55, …, 0,95. Строже: награждает точные рамки. Всегда ниже mAP@50.

Ориентиры для своего набора из нескольких сотен картинок: mAP@50 выше 0,8 — модель в целом годится; 0,5–0,8 — работает,
но ошибается, смотрите картинки из `eval.py`, чего не хватает; ниже 0,5 — мало или плохо размеченных данных. Цифры
на маленьком test «прыгают»: 15 картинок — это оценка «на глаз», не приговор.

### Train, valid, test

Размеченные картинки делят на три части:
- **train** (~70 %) — на них модель учится;
- **valid** (~15 %) — после каждой эпохи по ним считается mAP, выбирается лучшая версия весов и решается, когда
  остановиться. Модель на них не учится, но мы по ним принимаем решения — значит, немного под них подстраиваемся;
- **test** (~15 %) — откладываются и используются только в конце для честной оценки.

Главная ловушка — **утечка**: почти одинаковые кадры (соседние кадры одной серии) в train и test. Тогда test
проверяет запоминание, а не умение обобщать, и цифры завышены. Если снимали длинными сериями, лучше снять test
отдельно — в другой день, в другом месте.

### Аугментации

**Аугментации** — случайные изменения картинок во время обучения, чтобы модель видела больше разнообразия, чем есть
в данных. RF-DETR по умолчанию делает зеркальное отражение по горизонтали, обучение на нескольких масштабах
(multi-scale) и случайные вырезы с масштабированием. Цвет, освещение, размытие, ракурсы по умолчанию не меняются —
это разнообразие должно прийти из настоящих кадров. Если ваши классы отличаются зеркально (левый и правый ботинок),
отражение будет мешать.

### Переобучение

**Переобучение** — модель запомнила обучающие картинки вместо того, чтобы понять, как выглядит объект. Признаки:
- потери (loss) на train продолжают падать, а mAP на valid перестал расти или падает (`metrics.csv`);
- на train почти идеально, на test и на живом видео заметно хуже;
- модель находит объект только на «знакомом» фоне или в знакомом ракурсе.

Что помогает: больше разнообразных данных (лучшее средство), ранняя остановка (`train.py` останавливается, если
10 эпох нет улучшения на valid, и сохраняет лучшую версию), меньше эпох, модель поменьше. Обратная ситуация —
**недообучение**: плохо и на train, и на valid; нужно больше эпох или данных получше.

### Сколько нужно данных

Дообучение начинается не с нуля: модель уже умеет видеть объекты по COCO, ей нужно выучить только ваши. Ориентиры:
- **проба**: 50–100 рамок на класс, 100–200 картинок — модель уже что-то находит в знакомых условиях;
- **рабочая модель**: 200–500 рамок на класс из разных условий;
- **надёжная**: 1000+ рамок на класс; дальше качество растёт медленно, важнее разнообразие, чем количество;
- **фоновые кадры** (без ваших объектов, но в той же обстановке): 5–15 % набора — сильно уменьшают ложные срабатывания.

Число классов почти не влияет на скорость модели, но каждому классу нужны свои примеры.

### Как снимать свои объекты

- Снимайте **той же камерой и в тех же условиях**, где модель будет работать: HitCam с телефона, ваша комната,
  ваш свет. Лучшие данные — кадры из реального использования.
- **Разнообразие важнее количества**: разные ракурсы (сверху, сбоку, под углом), расстояния, повороты, фоны,
  освещение (день, лампа, полумрак), положения в кадре (не только в центре, но и у краёв).
- Объект **частично закрыт** рукой или другим предметом — тоже нужные примеры.
- **Несколько объектов** в кадре, разные экземпляры одного класса (кружки разных цветов, если класс — «кружка»).
- **Похожие, но не ваши** предметы в кадре без разметки — модель научится их не путать.
- **Размер**: вход Nano — 384 точки по ширине. Объект меньше ~20 точек на входе модели (примерно 100 точек в кадре
  1920×1080) она находит плохо — подойдите ближе или возьмите Small (512).
- Движение и лёгкая размытость в кадрах — это нормально: живое видео тоже такое. Совсем смазанные кадры удалите.
- Меняйте сцену между кадрами: 50 почти одинаковых кадров дают модели немногим больше, чем один.
